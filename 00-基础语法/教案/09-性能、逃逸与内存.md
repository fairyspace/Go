## 1. 教学目标

### 1.1 知识目标
1. 能读懂基准测试输出的四列（`N`、`ns/op`、`B/op`、`allocs/op`），并说出**为什么 `allocs/op` 通常是首要指标**。
2. 能说出字符串 `+` 累加是 O(n²) 的**原因**（每轮分配新数组并复制全部内容），而不是只记一个倍数。
3. 能说出逃逸的含义、查看命令，以及三种典型逃逸场景与各自的正确应对。

### 1.2 能力目标
1. 写规范的 `Benchmark`（`b.Loop()` / `b.ResetTimer()`、初始化放循环外）。
2. 用 `go build -gcflags='-m -l'` 定位逃逸，并做出正确优化。
3. 用 `pprof` 定位 CPU / 内存热点。

### 1.3 素养目标
1. **先测量，再优化**。没有基准数据的优化都是猜测。
2. **优化优先级按数量级排**：先改算法复杂度，再抠分配。
3. `sync.Pool` 是**最后手段**，不是"看起来高级就该用"。

## 5. 讲授要点（含板书）

### 5.1 板书一：Benchmark 怎么写、怎么读

```go
func BenchmarkXxx(b *testing.B) {
	// 初始化放循环外（被测对象的构造不是被测行为）
	enc := NewEncoder(key)

	b.ResetTimer()          // 排除初始化耗时
	for b.Loop() {          // Go 1.24+；旧版本写 for i := 0; i < b.N; i++
		enc.Encode(payload)
	}
}
```

```bash
go test -bench . -benchmem -benchtime=1s -count=5 ./s16_bench
```

输出四列的含义：
```text
BenchmarkMD5-8    3000000    297.0 ns/op    32 B/op    1 allocs/op
                  ↑          ↑              ↑          ↑
              执行次数    每次耗时      每次分配字节  每次分配次数
             -8 = GOMAXPROCS
```

**怎么读**
1. **`allocs/op` 优先**：分配次数直接决定 GC 压力，而 GC 压力往往是真实服务的延迟来源。
2. `ns/op` 受机器影响大，**跨机器不要直接比数字**。
3. `-count=5` 跑多轮，配合 `benchstat` 判断差异是否显著；单轮 100 次的数据（讲义里 `81.00 ns/op` 那种）**噪声大于信号**，不能当结论。
4. **初始化必须在循环外**。讲义里 `New().Encrypt("123456")` 把对象构造也测进去了（勘误 A10 相关）。

### 5.2 板书二：字符串拼接（勘误 A8）

```go
// ❌ 循环里累加：O(n²)
s := ""
for i := 0; i < n; i++ {
	s += "golang"          // 每轮分配新串 + 复制已有内容
}

// ❌ Sprintf 累加：更慢（还要解析格式串 + 反射）
s = fmt.Sprintf("%s%s", s, "golang")

// ✅ strings.Builder + 预分配
var sb strings.Builder
sb.Grow(n * len("golang")) // 关键：一次分配到位
for i := 0; i < n; i++ {
	sb.WriteString("golang")
}
s := sb.String()
```

**⚠️ 必须澄清的错误认知**：讲义写「Go 1.11+ 编译器会把循环里的 `s += "golang"` 改写为 `strings.Builder`」——**这是错的**。
- 编译器只会把**同一条表达式内**的 `a + b + c` 折叠成一次 `runtime.concatstrings`（一次分配）；
- **跨迭代的累加不会被改写**，每轮仍然分配 + 复制。
- 反证：讲义自己的数据 `BenchmarkStringOp1-8 ... 999 allocs/op`——如果真被优化了，就不会有 999 次分配。

**什么时候可以放心用 `+`**
```go
s := "id=" + id + "&name=" + name   // ✅ 单表达式，编译器一次分配
```

**`strings.Builder` 的注意**
- **不能复制**：`sb2 := sb` 之后再写会 panic（`illegal use of non-zero Builder copied by value`）；要传参就传 `*strings.Builder`。
- `bytes.Buffer` 与 `strings.Builder` 用途相同：前者面向 `[]byte`，后者面向 `string`。

### 5.3 板书三：`map[string]any` vs struct

```go
// ❌ 字段固定却用 map
demo := map[string]any{}
demo["Name"] = "Tom"
demo["Age"] = 30

// ✅ 临时 struct（栈上、零分配）
var demo struct {
	Name string
	Age  int
}
demo.Name = "Tom"
demo.Age = 30
```
差距来源：map 要**哈希 + 桶查找 + 值装箱**（把 `int`/`string` 装进 `any` 通常会分配）；struct 是**编译期确定的偏移量访问**。
> 讲义给的"117 倍"是特定环境的数据，**只记数量级**：字段固定用 struct，是免费的性能。

### 5.4 板书四：逃逸分析（勘误 A9）

```bash
go build -gcflags='-m -l' ./s17_escape   # -m 输出逃逸信息，-l 关闭内联（减少噪声）
go build -gcflags='-m -m' ./...          # 更详细的原因
```

**什么是逃逸**：编译器在**编译期**判断一个变量的生命周期是否超出当前函数；超出就分配到**堆**（需要 GC），否则分配到**栈**（函数返回即回收，几乎零成本）。

| 场景 | 代码 | 结果 | 正确应对 |
|---|---|---|---|
| ① 存进 `interface` | `stu.Name = "tom"`（`Name any`） | 值逃逸到堆 | 字段用**具体类型** |
| ② 返回指针 | `return stu` | 对象逃逸 | 视情况：能返回值就返回值 |
| ③ 对象过大 | `make([]int, 10000, 10000)` | 逃逸（超过栈上对象上限，gc 内部 `maxStackVarSize`，当前实现 64KB） | **复用缓冲区** / `sync.Pool`；**设 cap 不解决问题** |

> ⚠️ **勘误 A9**：讲义在场景③下写"优化方案：尽量设置容量"，因果不成立。
> - **预分配 `make([]T, 0, n)`** 解决的是 *append 反复扩容导致的多次分配与复制*；
> - **避免大对象逃逸**要靠"复用外层 buffer / 池 / 让对象不逃出函数"。
> 两件事必须分开讲，否则学生会以为"写了 cap 就不逃逸了"。

**传指针一定更快吗？不一定。**
```go
func f(p *SmallStruct)   // 小对象传指针 → 可能逃逸到堆 → 反而更慢
func f(v SmallStruct)    // 小对象传值 → 栈上复制几个字，通常更快
```
判据：**先用基准测**，别凭直觉。

### 5.5 板书五：`sync.Pool` 什么时候才值得（勘误 A11、A16）

```go
var bufPool = &sync.Pool{
	New: func() any { return new(bytes.Buffer) },
}

func handle() {
	buf := bufPool.Get().(*bytes.Buffer)
	defer func() {
		buf.Reset()          // ← 必须重置，否则脏数据 + 内存滞留
		bufPool.Put(buf)
	}()
	// 使用 buf
}
```

**四条纪律**
1. 只存**临时对象**：绝不能存 socket 长连接、数据库连接（它们需要生命周期管理，Pool 不提供）。
2. `Get` 后必须 `Put`（用 `defer` 兜底），否则池退化成普通分配。
3. `Put` 前必须 `Reset`，尤其是有大字段（slice/map）的对象。
4. **先证明它是热点**：`-benchmem` 显示该对象分配占大头，才考虑上池。

**GC 行为（勘误 A11）**
> 讲义说"每次 GC 都会清空 pool"不准确。**Go 1.13 起引入 victim cache**：GC 开始时把主缓存整体挪到 victim 区，**上一轮的 victim 才真正丢弃**。因此对象**最多两个 GC 周期内**被回收。这个设计正是为了避免"GC 后瞬间全量重建"的分配尖峰。
> 结论不变：**池不保证对象长期可用**，所以不能当连接池用。

**典型适用对象**：`bytes.Buffer`、大 `[]byte`、编解码器、解析过程中的中间对象。
**典型不适用**：几十字节的小结构体（如 07 篇的 `option`）——分配成本本来就接近零，池化省不掉 `WithXxx` 闭包的分配，却引入了 `reset` 漏字段导致脏数据的风险（勘误 A16）。

### 5.6 板书六：优化优先级与工具

**优先级（从高到低）**
| 优先级 | 手段 | 典型收益 |
|---|---|---|
| 1 | 改算法复杂度（O(n²) → O(n log n)） | 数量级 |
| 2 | 消除循环内重复计算 / 重复 IO | 视情况 |
| 3 | 用 struct 替代 `map[string]any` | 数十倍 |
| 4 | `strings.Builder` + `Grow` 替代 `+` 累加 | 数十~上万倍（随规模变化） |
| 5 | 预分配 slice/map 容量 | 省掉多次扩容复制 |
| 6 | 消除 `any` 导致的逃逸 | 降 GC 压力 |
| 7 | 并行化（`errgroup` + 限流） | 视任务类型 |
| 8 | `sync.Pool` | 最后手段 |

```bash
# CPU 热点
go test -bench . -cpuprofile cpu.out ./pkg/xxx && go tool pprof -top cpu.out
# 内存分配
go test -bench . -memprofile mem.out ./pkg/xxx && go tool pprof -top mem.out
# 逃逸
go build -gcflags='-m -l' ./...
# 竞态（08 篇）
go test -race ./...
# 基准对比
go test -bench . -count=10 > old.txt   # 改代码后 > new.txt
benchstat old.txt new.txt
```

**黄金原则：先测量，再优化；优化后必须重新测量。**

## 6. 演示脚本

```go
package bench

import (
	"fmt"
	"strings"
	"testing"
)

// ---------- 被测函数 ----------

func concatPlus(n int) string {
	s := ""
	for i := 0; i < n; i++ {
		s += "golang"
	}
	return s
}

func concatBuilder(n int) string {
	var sb strings.Builder
	sb.Grow(n * len("golang"))
	for i := 0; i < n; i++ {
		sb.WriteString("golang")
	}
	return sb.String()
}

// ---------- 正确性测试：先保证对，再谈快 ----------

func TestConcat(t *testing.T) {
	want := strings.Repeat("golang", 10)
	if got := concatPlus(10); got != want {
		t.Errorf("concatPlus = %q", got)
	}
	if got := concatBuilder(10); got != want {
		t.Errorf("concatBuilder = %q", got)
	}
}

// ---------- 基准：初始化在循环外 ----------

func BenchmarkConcatPlus(b *testing.B) {
	b.ReportAllocs()
	for b.Loop() {
		_ = concatPlus(1000)
	}
}

func BenchmarkConcatBuilder(b *testing.B) {
	b.ReportAllocs()
	for b.Loop() {
		_ = concatBuilder(1000)
	}
}

// 对照：证明"编译器不会优化循环内的 +="
func BenchmarkConcatPlusSmall(b *testing.B) {
	b.ReportAllocs()
	for b.Loop() {
		_ = concatPlus(3) // 规模小时差距急剧缩小 → 说明差距来自 O(n²)
	}
}

var _ = fmt.Sprint
```

> **版本要求**：`for b.Loop()` 是 **Go 1.24** 新增的（官方发布说明：*"Benchmarks may now use the faster and less error-prone testing.B.Loop method"*）。它的两个好处正好治住两个常见错误——setup 只执行一次、循环体不会被编译器优化掉。工具链低于 1.24 时改回 `for i := 0; i < b.N; i++`，并自己保证这两点。
>
> 对应仓库示例：`s16_bench/`（注意该目录是**测试包**，用 `go test` 而非 `go run`，见勘误 B1）、`s17_escape/`、`s17_pool/`。仓库 `go.mod` 目前声明 `go 1.22`，若要用 `b.Loop()` 需先提升（勘误 B10）。

## 7. 课堂练习（含参考答案）

**练习 1** 下面基准有什么问题？改对。
```go
func BenchmarkMD5(b *testing.B) {
	for i := 0; i < b.N; i++ {
		New().Encrypt("123456")
	}
}
```
> **答**：`New()` 在循环内，把对象构造的开销也算进了 MD5 的性能。改为：
> ```go
> func BenchmarkMD5(b *testing.B) {
> 	enc := New()
> 	b.ReportAllocs()
> 	for b.Loop() {
> 		_ = enc.Encrypt("123456")
> 	}
> }
> ```
> （这也是勘误 A10 的根源：讲义据此得出"复用 cipher 对象"的结论，但代码里 `Encrypt` 每次都新建 cipher。）

**练习 2** 解释：为什么 `make([]int, 0, 10000)` 仍然会逃逸？那预分配还有意义吗？
> **答**：80000 字节超过栈上对象上限，所以逃逸到堆（勘误 A9）。预分配依然有意义——它把"从 0 增长到 10000 过程中的多次分配 + 复制"变成**一次分配**；只是这次分配发生在堆上。两件事解决的是不同问题。

**练习 3** 下面代码有一处会造成脏数据，找出来并修正。
```go
var pool = &sync.Pool{New: func() any { return &User{} }}

func handle(name string) {
	u := pool.Get().(*User)
	defer pool.Put(u)
	u.Name = name
	u.Tags = append(u.Tags, "vip")
	process(u)
}
```
> **答**：`Put` 前没有重置，`Tags` 会累积（下一个调用者拿到上一个人的 `Tags`，且 slice 一直增长导致内存滞留）。修正：
> ```go
> defer func() {
> 	u.Name = ""
> 	u.Tags = nil
> 	pool.Put(u)
> }()
> ```

**练习 4** 设计实验：证明"池化一个 48 字节的 option 结构体是无效优化"。
> **答**：写 `BenchmarkWithPool` / `BenchmarkWithoutPool` 两个基准，都用 `WithA()/WithB()/WithC()` 三个选项，`-benchmem` 对比 `allocs/op`。预期：两者的 `allocs/op` 都由**闭包分配**主导（每个 `WithXxx` 一次），池化省下的那一次结构体分配淹没在噪声里。若 `ns/op` 差异不显著（用 `benchstat` 判断），就应删掉池。

## 8. 勘误与易错预警

| 编号 | 讲义原说法 | 正确说法 |
|---|---|---|
| **A8** | Go 1.11+ 编译器会把循环里的 `+=` 改写为 Builder | **不会**。只有单表达式内的 `a+b+c` 会被折叠为一次分配 |
| **A9** | 大对象逃逸的优化方案是"设置容量" | 设 cap 不改变逃逸；预分配解决的是扩容复制 |
| **A10** | `s16_bench` 中 `NewAES` 复用了 cipher 对象 | `NewAES` 只存 key/iv，`Encrypt` 内部每次都 `aes.NewCipher` |
| **A11** | sync.Pool 每轮 GC 清空 | victim cache：**最多两个 GC 周期**内回收 |
| **A16** | 用 sync.Pool 池化小 option 是"合理场景" | 反模式；小对象分配成本近乎零，池化省不掉闭包分配 |
| **B9** | 三处粘贴两套环境的基准数据 | 数据只留一处，并注明平台/版本/`-benchtime`/`-count` |
| — | 学员记住"13000 倍""117 倍" | 倍数随规模剧变；**记原因，不记数字** |
| — | 学员用 `time.Now()` 做微基准 | 用 `testing.B`；短代码可能被编译器优化掉 |
