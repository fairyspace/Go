## 1. 教学目标

### 1.1 知识目标
1. 能准确描述 goroutine 与 OS 线程的关系（GMP 模型：G 由少量 M 承载），并说出它与线程的量级差异。
2. 能区分**并发**（结构：同时处理多件事的组织方式）与**并行**（执行：同一时刻真的在跑），并说出 Go **两者都有**。
3. 能说出 channel 的四条规则：无缓冲收发皆阻塞、缓冲满写阻塞/空读阻塞、`close` 后不可写、关闭由**发送方**负责。

### 1.2 能力目标
1. 用 WaitGroup 正确编排"等待全部完成"，并避开三个坑。
2. 用 Worker Pool 处理"固定并发度"的任务队列。
3. 用 `-race` 定位数据竞争。

### 1.3 素养目标
1. **不要用 `time.Sleep` 等待 goroutine**——用 WaitGroup 或 channel。
2. **每个 goroutine 入口自己 `recover`**，否则一个 panic 崩掉整个进程。
3. 并发代码**默认开 `-race` 跑一遍**。

## 2. 重点与难点

| | 内容 | 处理方式 |
|---|---|---|
| **重点** | channel 阻塞语义 + close 规则 | 现场制造一次死锁 |
| **重点** | WaitGroup 三个坑 | 每个坑现场演示一次 |
| **难点** | goroutine ≠ 线程（A6） | GMP 图 + 量级对比 |
| **难点** | "main 返回即进程退出"（不是"跑得快"） | 对比有无 Sleep 的输出 |

## 5. 讲授要点（含板书）

### 5.1 板书一：goroutine 不是线程（勘误 A6）

```
        你的代码
   G1  G2  G3 ... Gn        ← goroutine（G）：初始栈 2KB，可增长；数十万个没问题
        │  │  │
     ┌──┴──┴──┴──┐
     │  Go 运行时调度器  │   ← 把 G 分派到 M 上；阻塞时把 G 摘下来换别的
     └──┬──┬──┬──┘
        M1 M2 M3            ← OS 线程（M），数量约等于 GOMAXPROCS
        CPU 核 1 2 3
```

| | OS 线程 | goroutine |
|---|---|---|
| 创建成本 | 高（MB 级栈 + 内核对象） | 极低（2KB 栈，用户态） |
| 切换 | 内核态切换 | 用户态切换 |
| 数量级 | 数千 | 数十万 |
| 谁调度 | 操作系统 | Go 运行时 |

**并发 vs 并行（必须讲清）**
- **并发**：一种**结构**——同时"处理"多件事（可能在单核上交替）。
- **并行**：一种**执行状态**——同一时刻**真的同时**在跑（需要多核）。
- **Go 两者都有**：`GOMAXPROCS` 默认等于 CPU 核数（Go 1.25 起还会感知容器 cgroup 的 CPU 限额），多核上多个 goroutine 真并行。

> ⚠️ 讲义说"Go 的线程是并发机制，不是并行机制"是**错的**；它自己后面举的"一边看书一边接电话=并行"的例子恰好反驳了这句话。

**"为什么没打印 goroutine"的正确解释**
```go
func main() {
	fmt.Println("main start")
	go func() { fmt.Println("goroutine") }()
	fmt.Println("main end")
}
// 输出：main start / main end —— goroutine 那行大概率不出现
```
原因**不是"主线程跑得太快"**，而是：**`main` 返回即进程退出，未执行完的 goroutine 被直接终止**。哪怕子 goroutine 只需 1ns，也存在没被调度到的可能。`time.Sleep` 只是**碰运气**，不是同步手段。

### 5.2 板书二：channel 规则

```go
ch := make(chan string)      // 无缓冲：收发必须同时就绪
ch2 := make(chan string, 10) // 缓冲 10：满了写阻塞，空了读阻塞
```

| 操作 | 无缓冲 | 缓冲未满 | 缓冲已满 | 已 close |
|---|---|---|---|---|
| 发送 `ch <- v` | 阻塞至有人接收 | 立即返回 | 阻塞 | **panic** |
| 接收 `<-ch` | 阻塞至有人发送 | 立即返回 | 立即返回 | 取完余值后返回零值，`ok=false` |
| `close(ch)` | ✅ | ✅ | ✅ | **panic** |

**四条铁律**
1. `close` 只能由**发送方**调用（`close` 的签名是 `close(c chan<- Type)`，**只读通道不能 close**）。
2. 向已关闭的 channel 发送 → `panic: send on closed channel`；重复 close → `panic: close of closed channel`。
3. 关闭是**广播**：所有接收方都会收到"没有更多数据"的信号，适合一对多通知。
4. `for v := range ch` 只有在 channel **被 close** 后才退出；否则 goroutine 永久泄漏。

### 5.3 板书三：方向化 channel（勘误 A14）

```go
// ❌ 讲义写法：在 make 处限定方向
ch3 := make(<-chan string)   // 这个通道永远无法写入，读它必然永久阻塞
ch4 := make(chan<- string)   // 这个通道永远无法读取

// ✅ 正确：创建双向，在函数签名上约束
ch := make(chan string, 8)
go producer(ch)              // 隐式转换成 chan<- string
go consumer(ch)              // 隐式转换成 <-chan string

func producer(out chan<- string) { defer close(out); out <- "a" }
func consumer(in <-chan string)  { for v := range in { fmt.Println(v) } }
```

> **方向是给"使用者"的约束，不是给"创建者"的。** 创建时就限定方向，等于造了一个自己用不了的通道。

### 5.4 板书四：select 与 Worker Pool

```go
select {
case v := <-ch1:
	fmt.Println("ch1", v)
case ch2 <- "x":
	fmt.Println("写入 ch2")
case <-time.After(time.Second):
	fmt.Println("超时")            // 超时兜底
default:
	fmt.Println("都没就绪")         // 有 default 就不阻塞
}
```
- 全部 case 阻塞时，`select` 阻塞；
- **多个同时就绪时随机选一个**（防止饿死）；
- 带 `default` 时不阻塞（用于非阻塞收发）。

```go
func worker(id int, jobs <-chan int, results chan<- int) {
	for j := range jobs {          // jobs 关闭后自动退出
		results <- j * j
	}
}

func main() {
	jobs := make(chan int, 100)
	results := make(chan int, 100)

	for w := 1; w <= 3; w++ {      // 固定 3 个 worker
		go worker(w, jobs, results)
	}
	for j := 1; j <= 9; j++ {
		jobs <- j
	}
	close(jobs)                    // 关键：否则 worker 永久阻塞

	sum := 0
	for i := 0; i < 9; i++ {
		sum += <-results
	}
	fmt.Println("sum =", sum)      // 285
}
```
**三个要点**：① 方向化签名消除误用；② `close(jobs)` 让 worker 收工；③ **worker 数量固定**，不要来一个任务开一个 goroutine。

### 5.5 板书五：WaitGroup

```go
var wg sync.WaitGroup
wg.Add(3)                    // ← 必须在 go 之前
go task1(&wg)
go task2(&wg)
go task3(&wg)
wg.Wait()

func task1(wg *sync.WaitGroup) {
	defer wg.Done()
	// ...
}
```

**三个坑**

**坑 1：必须传指针**
```go
go task(wg)    // ❌ 传值
go task(&wg)   // ✅
```
> ⚠️ **勘误 A7**：讲义说"Go 1.20+ 传值会直接 panic：`sync: WaitGroup is copied before use`"是**错的**。
> `noCopy` 只是给 `go vet` 看的标记，**运行时什么都不做**。传值的真实后果是：副本有独立计数器，`Done()` 减的是副本，**原计数器永不归零 → `wg.Wait()` 永久阻塞**。
> `go vet` 会报 `passes lock by value: sync.WaitGroup`——这是**静态检查**（`go build` 不报，`go test` 默认会跑）。
> **教学意义**：不要把静态检查说成运行时 panic，否则学生调试时会去找一个永远不出现的 panic。

**坑 2：`Add` 不能放在 goroutine 内部**
```go
// ❌ 竞态：可能 Wait() 已经返回了才 Add
go func() { wg.Add(1); defer wg.Done(); ... }()
wg.Wait()
```
> `Add` 必须在**启动 goroutine 之前**执行，且在 `Wait()` 之前。

**坑 3：Add / Done 必须配平**
`Done()` 就是 `Add(-1)`；计数变负会 **panic**（`sync: negative WaitGroup counter`）。所以 `Done()` 一律用 `defer`。

**WaitGroup 的能力边界**
它只能"等全部完成"。**需要"一个失败就取消其余"**时，用 `context`：
```go
ctx, cancel := context.WithCancel(context.Background())
defer cancel()

go func() {
	select {
	case <-ctx.Done():
		log.Println("被取消:", ctx.Err())
	case r := <-results:
		log.Println("成功:", r)
	}
}()
```
> 生产环境首选 `golang.org/x/sync/errgroup`：返回第一个错误并自动取消其余任务，是 WaitGroup + context 的官方封装。

### 5.6 板书六：共享数据怎么选

| 场景 | 选择 |
|---|---|
| key 集合基本稳定、**读多写少**（配置缓存、路由表） | `sync.Map`（读路径无锁） |
| key 频繁增删、类型固定 | `map[K]V` + `sync.RWMutex` ✅ 默认选择 |
| 需要 `len()`、需要有序遍历 | `map` + `RWMutex`（`sync.Map` 只能 `Range` 计数） |
| 想避免 `any` 断言 | `map[K]V` + `RWMutex`（`sync.Map` 的 key/value 都是 `any`） |

```go
type SafeMap struct {
	mu sync.RWMutex
	m  map[string]int
}

func (s *SafeMap) Set(k string, v int) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.m[k] = v
}
func (s *SafeMap) Get(k string) (int, bool) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	v, ok := s.m[k]
	return v, ok
}
func (s *SafeMap) Len() int {
	s.mu.RLock()
	defer s.mu.RUnlock()
	return len(s.m)
}
```
> `sync.Map` **不是** `map` 的通用并发替代品。它的方法签名全是 `any`，丢失类型安全；`sync.Map` 也没有 `len()`。

### 5.7 板书七：并发安全 checklist

| 风险 | 症状 | 解法 |
|---|---|---|
| 数据竞争 | `-race` 报警 | 锁或 channel 保护所有共享数据 |
| 并发写 map | `fatal error: concurrent map writes` | `RWMutex` 或 `sync.Map` |
| goroutine 泄漏 | 协程数持续上涨 | 每个 `range ch` 都配 `close`；用 context 超时 |
| 子 goroutine panic | 整个进程退出 | **每个 goroutine 入口 `recover`** |
| 主协程提前退出 | 逻辑漏执行 | WaitGroup / channel 同步 |
| 死锁 | `all goroutines are asleep` | 检查无缓冲 channel 的收发顺序、锁顺序 |
| 循环内 defer | 资源到最后才释放 | 包成函数（06 篇） |

```go
// 标准 goroutine 模板
func safeGo(name string, fn func()) {
	go func() {
		defer func() {
			if r := recover(); r != nil {
				log.Printf("goroutine %s panic: %v\n%s", name, r, debug.Stack())
			}
		}()
		fn()
	}()
}
```

## 6. 演示脚本

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func main() {
	// 1) 进程退出 vs Sleep
	fmt.Println("1) main start")
	go func() { fmt.Println("   goroutine（可能来不及执行）") }()
	fmt.Println("   main end")

	// 2) 无缓冲 channel：发送方必须在 goroutine 里
	ch := make(chan string)
	go func() { ch <- "a" }()
	fmt.Println("2) 收到:", <-ch)

	// 3) 方向化在签名上
	tasks := make(chan int, 4)
	results := make(chan int, 4)
	var wg sync.WaitGroup
	wg.Add(2)
	go produce(tasks, 2)
	go func() { defer wg.Done(); consume(tasks, results) }()
	go func() {
		defer wg.Done()
		sum := 0
		for i := 0; i < 2; i++ {
			sum += <-results
		}
		fmt.Println("3) 平方和:", sum)
	}()
	wg.Wait()

	// 4) select 超时
	slow := make(chan string, 1)
	go func() { time.Sleep(200 * time.Millisecond); slow <- "done" }()
	select {
	case v := <-slow:
		fmt.Println("4)", v)
	case <-time.After(50 * time.Millisecond):
		fmt.Println("4) 超时（预期走这里）")
	}

	// 5) 共享计数器：必须加锁
	var counter int
	var mu sync.Mutex
	var wg2 sync.WaitGroup
	for i := 0; i < 10; i++ {
		wg2.Add(1)
		go func() {
			defer wg2.Done()
			for j := 0; j < 1000; j++ {
				mu.Lock()
				counter++
				mu.Unlock()
			}
		}()
	}
	wg2.Wait()
	fmt.Println("5) 并发累加:", counter) // 10000（去掉锁会得到随机小于 10000 的值）
}

func produce(out chan<- int, n int) {
	defer close(out)
	for i := 1; i <= n; i++ {
		out <- i
	}
}

func consume(in <-chan int, out chan<- int) {
	for v := range in {
		out <- v * v
	}
}
```

## 7. 课堂练习（含参考答案）

**练习 1** 下面代码为什么可能永久卡住？两种修法。
```go
func main() {
	ch := make(chan int)
	ch <- 1
	fmt.Println(<-ch)
}
```
> **答**：无缓冲 channel 的发送必须等接收方就绪，而接收在发送之后——main 卡在 `ch <- 1`，且没有其他 goroutine，运行时报 `all goroutines are asleep - deadlock!`。修法一：`ch := make(chan int, 1)`（缓冲）；修法二：把发送放进 goroutine（`go func(){ ch <- 1 }()`）。

**练习 2** 指出下面代码的问题，并说明**运行时的真实表现**（不要说 panic）。
```go
var wg sync.WaitGroup
wg.Add(1)
go func(wg sync.WaitGroup) {
	defer wg.Done()
}()  // 注意：这里没传参，实际是拷贝外层 wg
wg.Wait()
```
> **答**：形参 `wg` 是**值拷贝**，`Done()` 减的是副本的计数器，外层的 `wg` 计数仍为 1 → `wg.Wait()` **永久阻塞**（勘误 A7）。`go vet` 会报 `passes lock by value`。修法：传 `*sync.WaitGroup`。

**练习 3** 实现 `func ParallelFetch(urls []string, limit int) []Result`：并发抓取，最多 `limit` 个同时进行，任一失败不影响其他，返回结果顺序与入参一致。
> **答**（要点）：
> ```go
> func ParallelFetch(urls []string, limit int) []Result {
> 	results := make([]Result, len(urls))  // 预分配，按 index 写入 → 无需锁
> 	sem := make(chan struct{}, limit)     // 信号量控制并发度
> 	var wg sync.WaitGroup
> 	for i, u := range urls {
> 		wg.Add(1)
> 		go func(i int, u string) {
> 			defer wg.Done()
> 			sem <- struct{}{}
> 			defer func() { <-sem }()
> 			defer func() {
> 				if r := recover(); r != nil {
> 					results[i] = Result{Err: fmt.Errorf("panic: %v", r)}
> 				}
> 			}()
> 			results[i] = fetch(u)
> 		}(i, u)
> 	}
> 	wg.Wait()
> 	return results
> }
> ```
> 关键技巧：**按 index 写入预分配切片**，每个 goroutine 写不同的下标，天然无竞争，不需要锁。

**练习 4** 讨论：什么时候用 `sync.Map`，什么时候用 `RWMutex + map`？给出你的判据。
> **答**：默认 `RWMutex + map`（类型安全、有 `len`、行为可预期）。只有当 profiling 证明"读远多于写 + key 集合稳定 + 读锁成为瓶颈"时才换 `sync.Map`。**先测量再选择。**

## 8. 勘误与易错预警

| 编号 | 讲义原说法 | 正确说法 |
|---|---|---|
| **A6** | goroutine 是线程；Go 只并发不并行 | goroutine 是运行时调度的用户态执行单元；**Go 既并发也并行**（`GOMAXPROCS`） |
| **A6** | 没打印是因为"主线程太快" | **`main` 返回即进程退出**，未完成的 goroutine 被终止 |
| **A7** | 传值 WaitGroup 会 panic | **不会 panic**；后果是 `Wait()` 永久阻塞，`go vet` 静态告警 |
| **A14** | `make(<-chan string)` 声明只读通道 | 创建永远用双向；方向写在**函数签名**上 |
| — | 学员用 `time.Sleep` "等 goroutine" | 反模式；用 WaitGroup / channel / context |
| — | 学员在接收方 `close(ch)` | 由**发送方** close；接收方 close 会导致发送方 panic |
| — | 学员在循环里 `go func(){ ... i ... }()` | Go ≤1.21 会共享 `i`；Go ≥1.22 已修复，但读老代码要认得 |

## 9. 课后作业（分层）

- **基础**：用 WaitGroup 并发计算 1~100 的分段和（4 个 goroutine），结果写入预分配切片的各自下标，最后汇总。要求 `-race` 无警告。
- **进阶**：实现 `safeGo` + `ParallelFetch`（练习 3），支持传入 `context.Context` 以支持取消；写单测覆盖：全部成功、部分失败、上下文取消。
- **挑战**：实现一个"限流 + 超时 + 重试"的抓取器：
  - 最多 N 个并发（信号量）；
  - 每个请求超时 2s（`context.WithTimeout`）；
  - 失败重试 2 次（指数退避）；
  - 全程无数据竞争，且任一 goroutine panic 不影响整体。
  要求用 `testing/synctest`（Go 1.25+）或注入时钟来测试超时逻辑，**不要用真实 Sleep**。
