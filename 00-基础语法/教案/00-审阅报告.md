## A 类：技术性错误

### A1 ⚠️ 高危 ｜「`fmt.Printf` 不可以直接传整型字面量」

- **位置**：`教学文稿/02-变量、常量与数据类型.md`（输出方法表格 + 结尾 ⚠️ 框）
- **原文**：
  > `fmt.Printf` … **整型字面量不可以直接传**
  > ⚠️ 传整型字面量（如 `Printf("%d", 30)`）会报 `%!d(int=30)`，因为字面量默认是 `int` 而格式串期望 `uint` 类。
- **问题**：完全错误。`fmt.Printf("%d", 30)` 正常输出 `30`。`%d` 接受**任意整型**（含无符号），"期望 uint 类"这个解释是编造的。`%!d(...)` 这种错误串只在动词与实参类型不兼容时出现，例如 `fmt.Printf("%s", 30)` → `%!s(int=30)`。
- **溯源**：原文 `02-变量声明.md:147` 写的是「fmt.Printf：仅输出格式化的字符串和字符串变量（整型和整型变量不可以）」。这本身就是错的（作者当年大概是被 `%s` 坑过），教学文稿不但没有纠正，反而补了一段更"像样"的错误解释——**这是本次审阅最需要警惕的模式：把原文的错误合理化**。
- **依据**：`pkg.go.dev/fmt`：`%d` = base 10，用于整数；`%!v(T=value)` 是"动词与操作数类型不匹配"的报错格式。
- **修正**：占位符必须与实参**类型匹配**（`%d` 对整型、`%s` 对字符串/`Stringer`、`%v` 对任意类型）；不确定时用 `%v`。删掉"字面量不可以传"的整段说法。

### A2 ｜「常量不赋值时取该类型的默认值」

- **位置**：`教学文稿/02`（常量声明小节）
- **原文**：「`const 变量名称 数据类型 = 变量值` —— 如果不赋值，使用的是该数据类型的默认值」
- **问题**：常量**必须初始化**。`const x int`（无表达式）编译不通过，报 `missing init expr`。唯一可以省略表达式列表的场合是**括号分组内**复用上一行的表达式与类型（`iota` 枚举正是靠这条规则）。
- **依据**：Go 语言规范 *Constant declarations*：括号分组中「the expression list may be omitted from any but the first ConstSpec」。
- **修正**：常量必须有初始值；"零值"是**变量**的概念，两者不要混讲。

### A3 ｜`json:"-"` 的语义讲反了

- **位置**：`教学文稿/04-结构体与 JSON.md`（tag 选项表格）
- **原文**：「`json:"-"` ｜ 该字段不参与序列化（只用于反序列化）」
- **问题**：`json:"-"` 对 **Marshal 和 Unmarshal 双向都跳过**，该字段完全不参与 JSON。想让字段名输出成字面量 `-`，要写 `json:"-,"`（带逗号）。
- **依据**：`pkg.go.dev/encoding/json` Marshal 文档：「As a special case, if the field tag is "-", the field is always omitted. Note that a field with name "-" can still be generated using the tag "-,".」Unmarshal 使用同一套字段匹配规则。
- **修正**：表格改为「`json:"-"`：该字段完全不参与 JSON（双向跳过）；`json:"-,"`：字段名为 `-`」。

### A4 ｜「雪花 ID `1759482245000000` 精度会丢失」——举例错误

- **位置**：`教学文稿/04`（第四·3 引起问题的原因）+ `codes/教学/s12_json/main.go`（注释 `// 1.759482245e+15 精度已丢失`）
- **原文**：「`float64` 只有 53 位有效精度（约 16 位十进制），超过 15 位的整数（雪花 ID 如 `1759482245000000`）即使不显示为科学计数法，**精度也会丢失**。」
- **问题**：这个例子举错了。`1759482245000000` ≈ 1.76e15，而 `2^53 = 9007199254740992` ≈ 9.01e15，**它小于 2^53，可以被 float64 精确表示**（`float64(1759482245000000) == 1759482245000000` 成立）。它只是被 `%v` 以科学计数法**显示**，不是精度丢失。
  用 Python 复核：`float(1759482245000000).is_integer()` 且 `int(float(v)) == v` → True；`float(9007199254740993)` → `9.007199254740992e+15`（这才丢精度）。
- **危害**：学生拿这个数字去写单测断言"精度丢失"，会发现断言不成立，进而怀疑整条结论。
- **修正**：把概念拆成两层——
  1. **显示问题**：`float64` 经 `%v` 输出时，有效位 ≥ 7 位就切换成科学计数法（`1234567` → `1.234567e+06`）。这是格式化行为，值没变。
  2. **精度问题**：整数绝对值 **> 2^53（9007199254740992）** 才会真正丢精度。典型受害者是 **19 位雪花 ID**（如 `7300000000000000001` → `7.3e+18`）、纳秒时间戳相乘的结果。
  两个问题的解法都是"别用 `map[string]interface{}` 接 ID"，但**成因不同，必须分开讲**。

### A5 ｜`strings` 示例的两个返回值算错了

- **位置**：`教学文稿/10-常用标准库速查.md`（三、strings 常用）
- **原文**：
  ```go
  s := "Hello, Go World"
  strings.LastIndex(s, "o")     // 8
  strings.Count(s, "o")         // 2
  ```
- **问题**：`"Hello, Go World"` 中 `o` 出现在下标 **4、8、11**（`Hell**o**, G**o** W**o**rld`）。所以 `LastIndex` 应为 **11**，`Count` 应为 **3**。（`Index(s, "Go") == 7` 是对的。）
- **依据**：逐字符下标核对（len=15）：H0 e1 l2 l3 o4 ,5 ␠6 G7 o8 ␠9 W10 o11 r12 l13 d14。
- **修正**：改为 `// 11` 与 `// 3`。这类"注释里写预期值"的示例，**必须实机跑一遍**，否则学生照着抄会怀疑自己。

### A6 ⚠️ 高危 ｜「goroutine 是线程」「Go 是并发不是并行」

- **位置**：`教学文稿/08-并发编程.md`（go 关键字小节）
- **原文**：
  > 在 `go` 关键字后面加一个函数，就可以创建一个**线程（goroutine）**
  > 我们清楚 Go 语言的线程是**并发**机制，不是**并行**机制。
- **问题**：两处都错。
  1. goroutine **不是**操作系统线程。它是 Go 运行时调度的用户态执行单元（GMP 模型里的 G），由数量少得多的 OS 线程（M）承载，初始栈仅 2KB 且可增长，单机可轻松创建数十万个。
  2. Go **既并发也并行**：`GOMAXPROCS` 默认等于 CPU 核数（Go 1.25 起还会感知容器 cgroup 的 CPU 限额），多核上多个 goroutine 是**真正同时执行**的。文档自己后面举的"一边看书一边接电话=并行"的例子，恰好反驳了它前面的结论。
- **附带问题**：「为什么没输出 goroutine？因为主线程执行太快了」——表述不准确。真正原因是 **`main` 返回即进程退出，未执行完的 goroutine 被直接终止**，与"快慢"无关（哪怕子 goroutine 只需 1ns，也存在来不及调度的可能）。
- **修正**：用 GMP 一句话讲清 + 明确"并发是结构，并行是执行"；把 Sleep 的问题定性为"进程退出"而非"速度"。

### A7 ⚠️ 高危 ｜「Go 1.20+ 传值 WaitGroup 会直接 panic」

- **位置**：`教学文稿/08`（闭坑指南 01）
- **原文**：「Go 1.20+ 传值 `sync.WaitGroup` 会直接 panic：`sync: WaitGroup is copied before use`（该类型含 `noCopy` 标记）」
- **问题**：`noCopy` 是一个空结构体，实现了 `Lock()/Unlock()`，**唯一作用是让 `go vet` 的 copylocks 检查看得见它**，运行时什么都不做，不会 panic。
  传值 `WaitGroup` 的真实后果是：副本持有独立计数器，`Done()` 减的是副本，**原计数器永远不归零，`wg.Wait()` 永久阻塞**（或在其它路径上表现为计数错乱）。
  `go vet` 会报 `passes lock by value: sync.WaitGroup contains sync.noCopy`——这是**静态检查**，`go build` 不报，`go test` 默认会跑 vet 才看得到。
- **依据**：`sync.WaitGroup` 源码注释与社区共识：noCopy「does absolutely nothing at runtime」，靠 vet 发现；官方文档只说「A WaitGroup must not be copied after first use」。
- **修正**：结论（必须传 `*sync.WaitGroup`）保留，理由改为"计数器不共享 → Wait 永久阻塞 + vet 静态告警"。**不要把静态检查说成运行时 panic**，否则学生调试时会去找一个永远不出现的 panic。

### A8 ⚠️ 高危 ｜「循环里的 `s += x` 会被编译器改写成 strings.Builder」

- **位置**：`教学文稿/09-性能调优.md`（小点 1「现代 Go 的最佳实践」场景 1）
- **原文**：
  ```go
  // 场景 1：循环内简单拼接——编译器会自动优化
  for i := 0; i < n; i++ {
      s += "golang" // Go 1.11+ 编译器会改写为 strings.Builder
  }
  ```
- **问题**：错误，而且是**会直接导致线上性能事故**的错误。编译器只会把**同一条表达式内**的 `a + b + c` 折叠为一次 `runtime.concatstrings`（一次分配、一次拷贝）；**跨迭代的累加 `s += x` 不会被改写成 Builder**，每轮仍要分配新串并复制已有内容，整体 O(n²)。
- **依据**：同一篇文档前面自己的基准数据就是反证——`BenchmarkStringOp1-8 1200190 ns/op 999 allocs/op`（`+` 循环 1000 次，999 次分配）。如果编译器真能优化掉，就不会有 999 次分配。
- **修正**：删除"编译器会自动优化"的说法。正确表述：
  - 单表达式 `x := a + b + c` → 编译器合并为一次分配，可放心用；
  - 循环累加 → **必须** `strings.Builder`（并 `Grow` 预分配）。

### A9 ｜逃逸场景 03 的"优化方案"因果不成立

- **位置**：`教学文稿/09`（可能出现逃逸的场景 · 03 栈空间不足）
- **原文**：「栈空间不足，会发生逃逸。**优化方案：尽量设置容量**（用 `make([]T, 0, n)` 预分配），如果容量实在过大那就没办法了。」
- **问题**：`make([]int, 10000, 10000)` 逃逸的原因是**对象体积超过栈上分配上限**（gc 内部常量 `maxStackVarSize`，当前实现 64KB；10000×8B = 80000B 已超），**设置 cap 不会改变这个结论**——`make([]int, 0, 10000)` 同样逃逸。把"预分配"当成"避免逃逸"的手段，是把第 04 篇的结论错误嫁接过来了。
- **修正**：区分两件事——
  - **预分配（`make([]T, 0, n)`）**解决的是 *append 反复扩容导致的多次分配与复制*，不解决逃逸；
  - **避免大对象逃逸**的手段是：复用外层缓冲区、`sync.Pool`、或让对象生命周期止于函数内（不返回指针、不存进 interface）。

### A10 ｜「s16_bench 中 NewAES 只创建一次，复用了 cipher 对象」与代码不符

- **位置**：`教学文稿/09`（结果汇总下的本机实测说明）
- **原文**：「这也是为什么实际项目中应复用 cipher 对象（见 `s16_bench` 中 `NewAES` 只创建一次的写法）」
- **问题**：`codes/教学/s16_bench/main.go` 里 `NewAES` 只是保存 `key`/`iv` 两个字段；`Encrypt`/`Decrypt` 内部**每次调用都执行 `aes.NewCipher(a.key)`**，并没有复用 `cipher.Block`。文档把一个不存在的优化说成范例。

### A11 ｜「sync.Pool 每轮 GC 都会清空」不准确

- **位置**：`教学文稿/09`（四、sync.Pool）+ `codes/教学/s17_pool/main.go` 的输出文案
- **原文**：「每次 GC 会清空 pool」／「原因：GC 会随时清空 pool（每轮 GC 都会）」
- **问题**：Go 1.13 起 sync.Pool 引入 **victim cache**：GC 开始时把主缓存整体挪到 victim 区，**上一轮的 victim 才真正丢弃**。因此一个对象至少能活过 2 个 GC 周期。这个机制正是为了避免"GC 后瞬间全量重建"的分配尖峰。
- **依据**：Go 源码提交 `2dcbf8b`（sync: smooth out Pool behavior over GC with a victim cache）：「objects will still be collected within two GCs (as opposed to one)」。
- **修正**：改为「GC 会把对象移入 victim 区，**最多两个 GC 周期内**被回收，因此池不保证对象长期可用」。结论不变：**不能用 Pool 存连接**。

### A12 ｜「Map 的 key 可以是任意类型」

- **位置**：`教学文稿/03-数组、切片与 Map.md`（三、映射 Map）
- **原文**：「Map 中的 key / value 可以是任意类型，但所有的 key 必须属于同一数据类型…」
- **问题**：**key 必须是可比较类型（comparable）**。slice、map、func 不能做 key（编译期报错）；含有这些字段的结构体也不能做 key；`interface{}` 做 key 时，若动态类型不可比较，运行时会 panic。value 才是任意类型。
- **修正**：明确写出 comparable 约束 + 一条"运行时 panic"的反例（`m[[]int{1}] = 1` 编译不过；`var k any = []int{1}; m[k] = 1` 运行时 panic）。

### A13 ｜「修改切片/Map 不用传指针」结论不完整

- **位置**：`教学文稿/06-函数、闭包与 defer.md`（常见指针写法速查表）
- **原文**：「修改切片/Map ｜ 不用传指针（切片含指针，Map 是引用类型）」
- **问题**：只对了一半。
  - **修改已有元素** `s[i] = v` / `m[k] = v`：不用传指针 ✅
  - **改变长度** `append` 触发扩容后，函数内的切片头指向**新数组**，调用方的切片头没变 → **调用方看不到** ❌
  要在函数内改长度，只能"返回新切片"（`s = f(s)`，Go 标准做法）或传 `*[]T`。
- **修正**：表格拆成两行；顺带纠正术语——**Go 没有"引用类型"**（见 C7）。

### A14 ｜`make(<-chan string)` 当"只读通道"示例

- **位置**：`教学文稿/08`（声明 chan）+ `codes/教学/s13_chan/main.go:25`
- **原文**：
  ```go
  ch3 := make(<-chan string)   // 只读通道
  ch4 := make(chan<- string)   // 只写通道
  ```
- **问题**：这是**语义上的坏示范**。`make(<-chan string)` 得到的是一个**永远无法写入**的通道，对它取值必然永久阻塞（若程序里没有别的 goroutine，就是死锁）；`make(chan<- string)` 则是一个永远无法读取的通道。方向化的意义在于**约束使用者**，它应当出现在**函数签名**上，而不是在 `make` 处：
  ```go
  ch := make(chan string, 8)          // 创建：永远用双向
  go producer(ch)                      // 隐式转换为 chan<- string
  go consumer(ch)                      // 隐式转换为 <-chan string
  func producer(out chan<- string) {}
  func consumer(in <-chan string) {}
  ```
  补充一个原文说对了的点：`close` 的签名是 `close(c chan<- Type)`，**只读通道不能 close**，关闭责任在发送方。
- **说明**：本条按"语义错误"处理（不主张它是编译错误）。该写法的编译行为请以本机 `go vet`/`go build` 复核为准——本次审阅在无 Go 工具链的环境完成，未实机验证（见文末"验证边界"）。

### A15 ｜示例用的是已废弃的 gRPC API

- **位置**：`教学文稿/07-接口与 Options 模式.md`（二、学习 grpc.Dial 的写法）
- **原文**：`grpc.Dial("127.0.0.1:8000", grpc.WithInsecure(), ...)`

- **依据**：`pkg.go.dev/google.golang.org/grpc`（函数文档已标注 deprecated）。
- **修正**：Options 模式的教学价值与具体 API 无关，教案保留模式讲解，代码示例改用 `grpc.NewClient` + `insecure.NewCredentials()`，并加一句"看到老项目里的 `Dial`/`WithInsecure` 该怎么迁移"。

### A16 ｜用 sync.Pool 池化一个 5 字段的 option 结构体（反模式）

- **位置**：`教学文稿/07`（代码实现 `s10_option/friend/option.go`）+ `codes/教学/s10_option/`
- **问题**：`option{sex,age,height,weight int; hobby string}` 约 48 字节，**分配成本近乎为零**；而每次调用 `WithSex(1)` 都会**为返回的闭包分配一次**（闭包捕获了参数），池化 option 省不掉这部分。净收益接近 0，代价却是：
  - 必须维护 `reset()`，漏一个字段就是**脏数据串号**（上一个请求的 hobby 泄漏到下一个请求）；
  - 读者要多理解一层对象池，教学信噪比下降。
- **依据**：`sync.Pool` 文档定位为"临时对象复用"，官方与社区一致的推荐场景是 `bytes.Buffer`、大 `[]byte`、编解码器等**分配代价高**的对象；Go 官方文档明确 Pool 是**性能优化的最后手段**（原文自己也引用了这句话，却在同一个 Demo 里违反了它）。
- **修正**：教案把这段改成**对照实验**——先给结构体参数版（推荐默认），再给 Options 版（为向后兼容），最后把 sync.Pool 版作为"什么时候才值得"的**反例讨论**，并保留 09 篇的 Pool 正确用法。

### A17 ｜类型断言示例里 `case *study` 永不可达

- **位置**：`教学文稿/07`（补充：类型断言）
- **原文**：
  ```go
  switch v := s.(type) {
  case interface{ Listen(string) string }:
      fmt.Println(v.Listen("music"))
  case *study:
      fmt.Println("具体类型:", v.Name)
  }
  ```
- **问题**：两点。① `*study` 实现了 `Listen(string) string`，**第一个 case 必然先命中**，第二个 case 是死代码；② `study` 是**包内私有**类型，这段代码放在 `main` 包里根本无法编译（`undefined: study`），与前文"私有结构体对外不可见"的教学点自相矛盾。
- **修正**：要么把示例放进 `study` 包内并说明作用域，要么把第二个 case 换成一个**真正不满足第一个接口**的类型，并加注释说明"类型 switch 按书写顺序匹配，先宽后窄是常见 bug"。

### A18 ｜交叉引用指错篇章

- **位置**：`教学文稿/02`（其他基础类型表格）
- **原文**：「`error` ｜ 错误接口，第 10 篇详述」
- **问题**：错误处理在 **06 篇**（函数与错误返回惯例）与 **10 篇速查**中各有一部分，但"详述"在 06 篇。02 篇此时学生还没学到函数返回值，指向 10 篇会让人翻到一个只有 API 表格的章节。
- **修正**：改为「错误接口，见第 06 篇『错误处理惯例』与第 10 篇『errors 与 fmt』」。同类问题：03 篇多处写"见第 09 篇"讲 map 性能，实际在 09 篇二；教案统一标注到小节。

### A19 ｜注释与代码互相矛盾

- **位置**：`教学文稿/04` + `codes/教学/s05_struct/main.go`
- **原文**：
  ```go
  p3 := Person{Name: "Aaron", Age: 32} // 忽略 Age
  ```
  以及「零值可用：`p1` 打印为 `{  0}`」
- **问题**：① `Age: 32` 明明赋了值，注释却说"忽略 Age"；要演示"部分字段初始化"应写 `p3 := Person{Name: "Aaron"}`。② 代码里 `p1` 已经被赋了 `Name/Age` 再打印，输出是 `{Tom 30}`，不是 `{  0}`；零值打印应该放在赋值**之前**。
- **修正**：代码与注释对齐，零值演示单独一行 `fmt.Printf("%+v\n", Person{})` → `{Name: Age:0}`。

### A20 ｜自相矛盾的推荐

- **位置**：`教学文稿/03`（常见用途）
- **原文**：「而字段固定时应使用 struct（第 04 篇）或 map[string]interface{}（性能差，见第 09 篇）。」
- **问题**：把"性能差、不推荐"的方案与推荐方案并列成"或"，句子逻辑自相矛盾；学生读完不知道该用哪个。
- **修正**：「字段固定 → struct；字段动态 → map；`map[string]interface{}` 只用于**结构确实未知**的透传场景（性能代价见 09 篇二）。」

## B 类：工程与一致性问题

### B1 ｜`s16_bench/main.go` 名为 main.go 却是 `package bench`

- **位置**：`codes/教学/s16_bench/main.go`、`main_test.go`

## C 类：教学法缺陷

### C1 ｜这不是"教案"，是"讲义"
现有 11 个文件是**内容组织得不错的讲义/教材**，但缺少教案的基本要素：课时数、教学目标（知识/能力/素养）、重难点、教学流程与时间分配、课堂练习与答案、考核点、板书设计。教师拿到手无法直接上课，必须自己二次备课。→ 本教案目录（`教案/01~11`）即为此补齐。

### C2 ｜节奏表按"周"排，与信息量不匹配
`00-索引` 的"学习节奏建议"：第 1 周 01~04 共 4 天、第 3 周只学 08 共 3 天。但按字数与信息密度，08 篇（16 KB）+ 09 篇（19 KB）是 01 篇（5 KB）的 3~4 倍，并发与性能的认知负荷远高于环境安装。→ 教案改为**按学时**排（共 20 学时），并给出每篇的课时数。

### C3 ｜验收标准不可观测
"能说清 defer 五个坑的输出顺序"是好标准，但多数条目是"能独立写出一个 struct + JSON 互转的工具"这类无法当场判定的表述。→ 教案每篇的"考核点"都写成**可观测行为**（能口述 / 能白板写出 / 能让 `go vet` 通过 / 能定位并修复给定的 bug）。

### C4 ｜"⚠️ 注意"堆叠，缺少分层
03 篇一口气出现 7 个 ⚠️，09 篇 9 个。初学者无法区分"现在必须记住"和"工作三年后再体会"。→ 教案统一三级标记：**【必知】**（考试与日常都用）／**【进阶】**（能读懂即可）／**【工程】**（生产环境才需要）。

### C5 ｜全课程没有测试视角
09 篇讲 Benchmark，但 20 个示例目录里只有 1 个 `_test.go`（s16_bench）。"先写测试再改代码"是 Go 工程最重要的习惯之一，应该在第 06 篇（函数）就植入。→ 教案从 06 篇起每篇配 1 个 `_test.go` 练习。

### C6 ｜缺少现代 Go 的衔接
课程止于 Go 1.22 的心智模型，没有为泛型（1.18）、迭代器（1.23）、`context` 深度使用、`slog` 结构化日志留下接口，学生学完直接看开源项目会断层。→ 教案在 07/10 篇加"延伸阅读"与"下一课预告"。

### C7 ｜术语不统一：Go 没有"引用传递"
文稿多处写「引用传递」「Map 是引用类型」「切片是引用类型」。**Go 只有值传递**：切片是一个含 `ptr/len/cap` 的结构体值，map 是一个指向 hmap 的指针值，传参时复制的都是这个"值"。把它叫"引用传递"会让学生在"为什么 append 后调用方看不到"（A13）这类问题上彻底混乱。→ 教案统一术语：
| 不要用 | 改用 |
|---|---|
| 引用传递 | **传指针** / **共享同一底层数据** |
| 引用类型 | **含指针的值类型**（slice header / map pointer / chan pointer） |
| 值传递（对比义） | **复制一份**，修改互不影响 |
