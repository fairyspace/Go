## 一、goroutine 与 channel

### go 关键字

原来分享基础语法的时候，还未分享过 chan 通道，这次把它补上。

chan 可以理解为队列，遵循**先进先出**的规则。

在说 chan 之前，咱们先说一下 `go` 关键字。

在 `go` 关键字后面加一个函数，就可以创建一个 **goroutine**，函数可以为已经写好的函数，也可以是匿名函数。

> ⚠️ **goroutine 不是操作系统线程**。它是 Go 运行时调度的**用户态执行单元**（GMP 模型中的 G），由数量少得多的 OS 线程（M）承载；初始栈仅 2KB 且可动态增长，单机轻松创建数十万个。而 OS 线程初始栈通常 1MB~8MB，创建成本高得多。原文「创建一个线程」的说法是错的。

举个例子：

```go
func main() {
	fmt.Println("main start")

	go func() {
		fmt.Println("goroutine")
	}()

	fmt.Println("main end")
}
```

输出：

```text
main start
main end
```

**为什么没有输出 goroutine？**

首先，我们清楚 Go 语言的线程是**并发**机制，不是**并行**机制。

那么，什么是并发，什么是并行？

- **并发**是不同的代码块**交替**执行，也就是交替可以做不同的事情
- **并行**是不同的代码块**同时**执行，也就是同时可以做不同的事情

举个生活化场景的例子：

> 你正在家看书，忽然电话来了，然后你接电话，通话完成后继续看书，这就是**并发**，看书和接电话交替做。
>
> 如果电话来了，你一边看书一边接电话，这就是**并行**，看书和接电话一起做。

> ⚠️ 原文「Go 语言的线程是并发机制，不是并行机制」**是错的**。Go **既并发也并行**：
> - **并发是结构**（怎么组织代码：goroutine、channel），**并行是执行**（多核同时跑）
> - `GOMAXPROCS` 默认等于 CPU 核数（Go 1.25 起还会感知容器 cgroup 的 CPU 限额），多核机器上多个 goroutine 是**真正同时执行**的
> - 上面"一边看书一边接电话"的例子本身就是并行，恰好反驳了原文的结论

说回上面的例子，为什么没有输出 goroutine？

> 真正的原因是：**`main` 函数返回即进程退出，还没执行完的 goroutine 会被直接终止**——与"快慢"无关。哪怕子 goroutine 只需要 1ns，也存在还没来得及被调度进程就退出的可能。
>
> 原文说"主线程执行太快了"并不准确：这不是速度问题，而是**生命周期**问题。

现在让主 goroutine 休眠 1 秒钟，再试试：

```go
func main() {
	fmt.Println("main start")

	go func() {
		fmt.Println("goroutine")
	}()

	time.Sleep(1 * time.Second)

	fmt.Println("main end")
}
```

输出：

```text
main start
goroutine
main end
```

这就对了。

> ⚠️ 用 `time.Sleep` 等待 goroutine 是**反模式**（结果不确定），生产代码用 `sync.WaitGroup` 或 `channel`。接下来，看看如何使用 chan。

### 声明 chan

```go
// 声明不带缓冲的通道
ch1 := make(chan string)

// 声明带 10 个缓冲的通道
ch2 := make(chan string, 10)
```

> ⚠️ **不要写 `make(<-chan string)` 或 `make(chan<- string)`**。
> 前者得到的通道**永远无法写入**，对它取值必然永久阻塞（没有其他 goroutine 时就是死锁）；后者得到的通道**永远无法读取**。它们对教学毫无价值，只会制造死锁。
>
> **方向化的真正用法是约束函数签名**——创建时永远用双向通道，把方向约束写在参数上：

```go
ch := make(chan string, 8) // 创建：永远用双向

go producer(ch) // 隐式转换为 chan<- string（只能写入）
go consumer(ch) // 隐式转换为 <-chan string（只能读取）

func producer(out chan<- string) { out <- "x" } // 只能写，写错方向编译器立即报错
func consumer(in <-chan string)  { fmt.Println(<-in) } // 只能读
```

> 方向化参数的价值：在 producer 内部尝试 `<-out` 会**编译失败**，把运行时错误提前到编译期。
>
> 补充：`close` 的签名是 `close(c chan<- Type)`——**只读通道不能 close**，关闭责任在发送方。

**注意**：

- 不带缓冲的通道，**进和出都会阻塞**
- 带缓冲的通道，进一次长度 +1，出一次长度 -1，如果长度等于缓冲长度时，再进就会阻塞

### 写入 / 读取 / 关闭 chan

```go
ch1 := make(chan string, 10)

ch1 <- "a"        // 写入
val := <-ch1      // 读取
val, ok := <-ch1  // 带 ok：通道关闭时 ok 为 false
close(ch1)        // 关闭
```

**注意**：

- `close` 以后**不能再写入**，写入会出现 `panic: send on closed channel`
- **重复 `close`** 会出现 `panic: close of closed channel`
- **只读的 chan 不能 `close`**
- `close` 以后**还可以读取数据**，读完得到零值且 `ok` 为 `false`

> **约定**：由**发送方**负责 `close`，接收方不负责关闭。关闭一个 channel 会**广播**给所有接收方，适合「任务完成」这类一对多通知场景。

### 示例一：死锁

```go
func main() {
	fmt.Println("main start")
	ch := make(chan string)
	ch <- "a" // 入 chan，无缓冲，写入即阻塞
	go func() {
		val := <-ch // 出 chan
		fmt.Println(val)
	}()
	fmt.Println("main end")
}
```

输出：

```text
main start
fatal error: all goroutines are asleep - deadlock!
```

**What ? 这是为啥，刚开始就出师不利呀？**

因为，定义的是一个无缓冲的 chan，**赋值后就陷入了阻塞**。`main` 被阻塞，goroutine 得不到调度机会，所有 goroutine 都休眠 → 死锁。

怎么解决它？声明一个有缓冲的 chan。

### 示例二：有缓冲，但主线程还是太快

```go
func main() {
	fmt.Println("main start")
	ch := make(chan string, 1)
	ch <- "a"
	go func() {
		val := <-ch
		fmt.Println(val)
	}()
	fmt.Println("main end")
}
```

输出：

```text
main start
main end
```

为啥没有输出 `a`？和前面一样，**`main` 返回时进程直接退出**，子 goroutine 被终止，加个休眠 1 秒钟，再试试：

```go
func main() {
	fmt.Println("main start")
	ch := make(chan string, 1)
	ch <- "a"
	go func() {
		val := <-ch
		fmt.Println(val)
	}()
	time.Sleep(1 * time.Second)
	fmt.Println("main end")
}
```

输出：

```text
main start
a
main end
```

这就对了。

### 示例三：正确的写法

```go
func main() {
	fmt.Println("main start")
	ch := make(chan string)
	go func() {
		ch <- "a" // 入 chan
	}()
	go func() {
		val := <-ch // 出 chan
		fmt.Println(val)
	}()
	time.Sleep(1 * time.Second)
	fmt.Println("main end")
}
```

输出：

```text
main start
a
main end
```

> 对比示例一：把「入」放到 goroutine 里，**发送方不再阻塞**，main 可以继续派发接收方。**无缓冲 channel 必须由 goroutine 来完成发送**。

### 示例四：生产者-消费者

```go
func producer(ch chan string) {
	fmt.Println("producer start")
	ch <- "a"
	ch <- "b"
	ch <- "c"
	ch <- "d" // 缓冲区为 3，第 4 次写入阻塞
	fmt.Println("producer end")
}

func customer(ch chan string) {
	for v := range ch { // range 会在通道关闭时自动结束循环
		fmt.Println(v)
	}
}

func main() {
	fmt.Println("main start")
	ch := make(chan string, 3)
	go producer(ch)
	go customer(ch)

	time.Sleep(1 * time.Second)
	fmt.Println("main end")
}
```

> 如果只有 producer 没有 customer，输出是：`producer start` → `main end`（producer 卡在第 4 次写入，看不到 `producer end`）。
>
> 有 customer 时，输出：`producer start` → `producer end` → `a b c d` → `main end`。

> ⚠️ 注意 `for v := range ch` 需要 **channel 被 close** 才会退出循环。示例中因为 `Sleep` 兜底所以没死锁，生产代码里**必须 `close(ch)`**，否则 consumer goroutine 永久泄漏。

### 补充：select 多路复用

```go
select {
case v := <-ch1:
	fmt.Println("ch1:", v)
case v := <-ch2:
	fmt.Println("ch2:", v)
case ch3 <- "x":
	fmt.Println("写入 ch3")
case <-time.After(1 * time.Second):
	fmt.Println("超时")
}
```

> select 会阻塞直到**至少有一个 case 就绪**；全部阻塞时一起阻塞；**有多个就绪时随机选一个**（避免饿死）。

### 补充：Worker Pool（生产环境常用形态）

```go
func worker(id int, jobs <-chan int, results chan<- int) {
	for j := range jobs {
		results <- j * j
	}
}

func main() {
	jobs := make(chan int, 100)
	results := make(chan int, 100)

	// 启动 3 个 worker
	for w := 1; w <= 3; w++ {
		go worker(w, jobs, results)
	}

	// 派发任务
	for j := 1; j <= 9; j++ {
		jobs <- j
	}
	close(jobs) // 通知所有 worker 收工

	// 收集结果
	sum := 0
	for i := 0; i < 9; i++ {
		sum += <-results
	}
	fmt.Println("sum =", sum) // sum = 285
}
```

三个要点：

1. `jobs` 用**只读方向**传入 worker（`jobs <-chan int`），**只写方向**传出 results（`chan<- int`）——**方向化 channel 消除误用**。
2. `close(jobs)` 是关键——否则 `range jobs` 永不结束，worker 永久泄漏。
3. 固定 worker 数量，避免无限制创建 goroutine 打爆系统。

## 二、sync.WaitGroup 编排并发任务

如果你有一个任务可以分解成多个子任务进行处理，同时每个子任务没有先后执行顺序的限制，等到全部子任务执行完毕后，再进行下一步处理。这时每个子任务的执行可以并发处理，这种情景下适合使用 `sync.WaitGroup`。

虽然 `sync.WaitGroup` 使用起来比较简单，但是一不留神很有可能踩到坑里。

### 正确使用

比如，有一个任务需要执行 3 个子任务，那么可以这样写：

```go
// s14_waitgroup/main.go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var wg sync.WaitGroup

	wg.Add(3) // 必须在 go 之前

	go handlerTask1(&wg)
	go handlerTask2(&wg)
	go handlerTask3(&wg)

	wg.Wait() // 等待全部完成

	fmt.Println("全部任务执行完毕.")
}

func handlerTask1(wg *sync.WaitGroup) {
	defer wg.Done()
	fmt.Println("执行任务 1")
}

func handlerTask2(wg *sync.WaitGroup) {
	defer wg.Done()
	fmt.Println("执行任务 2")
}

func handlerTask3(wg *sync.WaitGroup) {
	defer wg.Done()
	fmt.Println("执行任务 3")
}
```

输出：

```text
执行任务 3
执行任务 1
执行任务 2
全部任务执行完毕.
```

> 注意：任务**完成顺序是随机的**，这正是并发的意义。

### 闭坑指南

#### 01：必须传指针

```go
go handlerTask1(&wg) // 正确
go handlerTask1(wg)  // 错误
```

> 执行子任务时，必须传 `*sync.WaitGroup`，让所有 goroutine 共享**同一个计数器**。
>
> **传值的真实后果**：副本持有独立计数器，`wg.Done()` 减的是副本的计数，**原计数器永远不归零 → `wg.Wait()` 永久阻塞**（程序卡死）。
>
> **关于 panic 的澄清**：`sync.WaitGroup` 内部的 `noCopy` 是一个空结构体，它**只让 `go vet` 的 copylocks 检查能发现拷贝行为**（报 `passes lock by value: sync.WaitGroup contains sync.noCopy`），**运行时什么都不做、不会 panic**。`go build` 不报；`go test` 默认会跑 vet，所以在测试里能看到。不要去找一个永远不出现的 panic。

#### 02：注意不要将 `wg.Add()` 放在 `go handlerTask1(&wg)` 中

例如：

```go
// 错误
var wg sync.WaitGroup

go handlerTask1(&wg)

wg.Wait()

func handlerTask1(wg *sync.WaitGroup) {
	wg.Add(1) // 错误！可能 Wait 已经返回
	defer wg.Done()
	fmt.Println("执行任务 1")
}
```

> 注意 `wg.Add()` 一定要在 `wg.Wait()` 执行前执行！
>
> 这是典型的竞态：可能在 `wg.Wait()` 已经返回后才 `Add`，导致**任务还没开始，主流程就继续往下走了**。

#### 03：注意 `wg.Add()` 和 `wg.Done()` 的计数器保持一致

其实 `wg.Done()` 就是执行的 `wg.Add(-1)`。计数归零时 `Wait()` 返回，**计数为负会 panic**。

### 使用局限

`sync.WaitGroup` 使用起来比较简单，一定要注意不要踩到坑里。

其实 `sync.WaitGroup` 使用场景比较局限，**仅适用于等待全部子任务执行完毕后，再进行下一步处理**。

如果需求是「当第一个子任务执行失败时，通知其他子任务停止运行」，这时 `sync.WaitGroup` 是无法满足的，需要使用到**通知机制（`channel`）**：

```go
ctx, cancel := context.WithCancel(context.Background())
defer cancel() // 保证所有子任务都能收到取消信号

go func() {
	select {
	case <-ctx.Done():
		fmt.Println("任务被取消:", ctx.Err())
	case r := <-results:
		fmt.Println("成功:", r)
	}
}()
```

> 真实项目里**首选 `context.Context`**，它同时携带**取消信号、超时和请求级数据**。channel 是它的底层原理。
>
> `WaitGroup` 还有一个常见用途：**配合 `errgroup`**（`golang.org/x/sync/errgroup`），它是「返回第一个错误并自动取消其余任务」的官方封装，比裸用 WaitGroup 更贴合实际需求。

## 三、sync.Map 解决 map 并发安全问题

在 `Golang` 中 `map` **不是并发安全的**，自 1.9 才引入了 `sync.Map`。

`sync.Map` 的引入确实解决了 `map` 的并发安全问题，不过 `sync.Map` 却没有实现 `len()` 函数，如果想要计算 `sync.Map` 的长度，稍微有点麻烦，需要使用 `Range` 函数。

### map 并发操作出现问题

```go
func main() {
	demo := make(map[int]int)

	go func() {
		for j := 0; j < 1000; j++ {
			demo[j] = j
		}
	}()

	go func() {
		for j := 0; j < 1000; j++ {
			fmt.Println(demo[j])
		}
	}()

	time.Sleep(time.Second * 1)
}
```

执行输出：

```text
fatal error: concurrent map read and map write
```

### sync.Map 解决并发操作问题

```go
func main() {
	demo := sync.Map{}

	go func() {
		for j := 0; j < 1000; j++ {
			demo.Store(j, j)
		}
	}()

	go func() {
		for j := 0; j < 1000; j++ {
			fmt.Println(demo.Load(j))
		}
	}()

	time.Sleep(time.Second * 1)
}
```

执行输出：

```text
<nil> false
1 true
...
999 true
```

> `Load` 返回 `(value, ok)`，key 不存在时 `ok` 为 `false`。

### 计算 map 长度

普通 map：

```go
demo := make(map[int]int)
for j := 0; j < 1000; j++ {
	demo[j] = j
}
fmt.Println("len of demo:", len(demo))
```

执行输出：

```text
len of demo: 1000
```

### 计算 sync.Map 长度

`sync.Map` 只能通过 `Range` 遍历计数：

```go
demo := sync.Map{}
for j := 0; j < 1000; j++ {
	demo.Store(j, j)
}

lens := 0
demo.Range(func(key, value interface{}) bool {
	lens++
	return true // 返回 true 继续遍历，返回 false 提前终止
})

fmt.Println("len of demo:", lens)
```

执行输出：

```text
len of demo: 1000
```

### 六个方法小结

| 方法 | 作用 |
|---|---|
| `Load` | 加载 key 数据 |
| `Store` | 更新或新增 key 数据 |
| `Delete` | 删除 key 数据 |
| `Range` | 遍历数据（**唯一能求长度的方式**） |
| `LoadOrStore` | 如果存在 key 数据则返回，反之则设置 |
| `LoadAndDelete` | 如果存在 key 数据则删除 |

### 什么时候用 sync.Map

> ⚠️ **`sync.Map` 不是普通 map 并发安全的通用替代品**。这是最常见的误用。

`sync.Map` 的内部结构是「读多写少的 read-only 分支 + 加锁的 dirty map」，**只有 key 集合基本稳定时才能享受无锁读的优势**。

| 场景 | 建议 |
|---|---|
| key 集合基本不变，只是并发读写（如配置缓存、路由表） | ✅ `sync.Map` 优（命中 read-only 分支，无锁） |
| key 频繁增删，或类型固定单一 | ❌ 用 `map[K]V` + `sync.RWMutex` |
| 需要 `len()`、需要有序遍历 | ❌ 用 `map` + `RWMutex` |
| 只想避免写 `interface{}` 断言 | ❌ 用 `map[K]V` + `RWMutex` |

绝大多数场景的推荐写法：

```go
type SafeMap struct {
	mu sync.RWMutex
	m  map[string]int
}

func (s *SafeMap) Set(k string, v int) {
	s.mu.Lock()
	defer s.mu.Unlock()
	s.m[k] = v
}

func (s *SafeMap) Get(k string) (int, bool) {
	s.mu.RLock()
	defer s.mu.RUnlock()
	v, ok := s.m[k]
	return v, ok
}

func (s *SafeMap) Len() int {
	s.mu.RLock()
	defer s.mu.RUnlock()
	return len(s.m) // 有锁后可以直接 len
}
```

> 性能对比可参考第三方实现：https://github.com/orcaman/concurrent-map

## 四、并发安全 checklist

| 风险 | 症状 | 解决方案 |
|---|---|---|
| goroutine 泄漏 | 协程数量持续增长、内存上涨 | 为每个 `range` 的 channel 配 `close`；用 context 超时控制 |
| 数据竞争 | `-race` 报 warning | 所有共享数据用锁或 channel 保护 |
| 并发写 map | `fatal error: concurrent map writes` | `sync.Map` 或 `RWMutex` |
| 忘记 recover | 子 goroutine panic 崩整个进程 | **每个 goroutine 入口加 `defer recover()`**（第 05 篇） |
| 主协程提前退出 | 逻辑漏执行 | `WaitGroup` 或 channel 同步 |
| 死锁 | `all goroutines are asleep` | 检查无缓冲 channel 的收发顺序 |
| 循环内 defer | 资源累积到最后才释放 | 包成函数触发（见第 05 篇） |

**必备工具**：

```bash
go run -race main.go        # 竞态检测
go test -race ./...         # 测试时开启竞态检测
go vet ./...                # 静态检查
```

竞态检测器会明确指出读写冲突的位置，**它是并发问题排查的第一工具**。

### 标准 goroutine 模板

```go
func safeGo(name string, fn func()) {
	go func() {
		defer func() {
			if err := recover(); err != nil {
				log.Printf("goroutine %s panic: %v", name, err)
			}
		}()
		fn()
	}()
}
```

## 本篇要点

1. Go **既支持并发也支持并行**；goroutine 执行顺序不确定，**不要用 `time.Sleep` 等待**。
2. 无缓冲 channel 收发会阻塞；`close` 由**发送方**负责，重复 close 或向已关闭 channel 写会 panic。
3. `for v := range ch` 需要 `close(ch)` 才会退出，否则 goroutine 泄漏。
4. 用 `close(jobs)` + Worker Pool 模式；**方向化 channel**（`<-chan` / `chan<-`）消除误用。
5. `wg.Add()` 必须在 `go` 之前、且在 `wg.Wait()` 之前；`wg` 必须传指针。
6. WaitGroup 只解决「等全部完成」，**需要取消/通知用 context 或 errgroup**。
7. **不要滥用 `sync.Map`**——读多写少、key 固定才用；否则 `RWMutex` + `map` 更优。
8. **每个 goroutine 都要自己 `recover()`**。
9. 生产环境务必开 `-race`。
